# Раскрываемый контекст текущего диалога

Этот файл содержит доступную для раскрытия часть контекста, используемого в текущем разговоре.

Не включены:

- скрытые системные и служебные инструкции;
- автоматические обновления платформы и состояние инфраструктуры;
- внутренние рассуждения, промежуточное состояние модели и служебные вызовы инструментов;
- секреты, значения переменных окружения и закрытые данные интеграций;
- содержимое, которое могло бы раскрыть защищённые механизмы работы системы.

## Запрос и контекст расследования

Пользователь предоставил резюме предыдущего разговора:

### Цель

Проанализировать свежие production-логи ОСВ-dashboard, сопоставить повторяющуюся ошибку с предыдущим расследованием, определить устранённые и действующие гипотезы, обновить причины с вероятностями и не объявлять production полностью исправленным без подтверждения успешного durable restore.

### Установленные факты

- Production HTTP-процесс запускался, `/healthz` и основные страницы отвечали HTTP 200.
- Во время запуска встречались начальные ошибки и timeout маршрутизации.
- Durable restore завершался ошибкой `SSL connection has been closed unexpectedly`.
- После ошибки появлялись сообщения `durable restore failed`, `durable startup failed at stage restore` и `background startup failed`.
- Доступность HTTP и успешность durable restore рассматриваются как разные состояния.
- Успешный development startup не является подтверждением успешного production restore.

### Основная гипотеза

Главной действующей гипотезой была потеря PostgreSQL SSL-соединения во время длительного restore. Вероятность оценивалась примерно в 70–80%. Логи не позволяли точно отличить длинную транзакцию, сетевой timeout, ограничение времени жизни соединения, restart/failover базы или ресурсную проблему.

Отсутствие `pool_pre_ping`, recycle/retry и единственный commit в конце длительной операции повышали риск.

### Исключённые или ослабленные гипотезы

- Начальные healthcheck 500 и timeout в основном относились к startup-routing noise, а не к окончательной причине отказа restore.
- OOM не был доказан.
- `SIGABRT` создавался собственным watchdog для замены неотвечающего worker.
- Зелёный `/healthz` не доказывал восстановление финансовой истории.

### Открытые вопросы

- Что именно закрывало PostgreSQL-соединение: restart/failover, proxy timeout, lifetime соединения, лимит транзакции или ресурсная проблема.
- Каков размер production manifest и на какой операции происходил разрыв.
- Должны ли маршруты с финансовыми данными явно оставаться в recovery/degraded после ошибки restore.
- Нужен ли отдельный облегчённый startup probe.

## Выполненные изменения

В ходе текущего разговора были внесены следующие изменения.

### Подключение к PostgreSQL

В конфигурации SQLAlchemy включены:

- `pool_pre_ping`;
- `pool_recycle=180`.

Это предотвращает выдачу заведомо неработающего соединения из пула. Активная долгая транзакция дополнительно защищается checkpoint и retry.

### Повтор durable restore

При `OperationalError` restore:

- выполняет rollback;
- удаляет текущую SQLAlchemy-сессию;
- очищает пул соединений;
- повторяет операцию на новом соединении.

По умолчанию разрешены две попытки. Повтор ограничен ошибками соединения и не маскирует произвольные ошибки данных или приложения.

### Commit-checkpoint

JSON restore теперь фиксирует промежуточные результаты пакетами, по умолчанию каждые 250 обработанных строк.

Повторная попытка:

- пропускает уже восстановленные строки;
- повторно выполняет итоговую сверку указателей;
- исправляет PostgreSQL sequence даже тогда, когда строки были зафиксированы предыдущей попыткой;
- не перезаписывает существующий ненулевой указатель актуальной версии.

### Автоматическая проверка

Добавлен тест, моделирующий потерю соединения во время restore. Он подтверждает, что:

- первая попытка завершается `OperationalError`;
- создаётся свежая сессия и соединение;
- вторая попытка успешно завершает restore.

## Результаты проверок

- Целевой набор `test_durable_bootstrap.py`: 10 тестов прошли.
- Проверка синтаксиса Python прошла.
- Проверка diff на ошибки форматирования прошла.
- После перезапуска development workflow `/healthz` и `/` отвечали HTTP 200.
- Watchdog распознавал bounded startup и не создавал прежний цикл немедленных перезапусков worker.

Отдельный старый сценарий `test_durable_data.py` не завершился чисто: тестовый начальный пароль был отклонён текущей политикой, а затем сработала отдельная проверка фонового парсинга. Этот запуск не использовался как доказательство успешности нового retry-механизма.

## Текущая граница подтверждения

Production пока нельзя считать полностью исправленным.

Для подтверждения нужен новый production-запуск, в котором для одного worker присутствуют:

- `durable startup stage completed: restore`;
- `durable startup ready (restore=enabled)`;

и отсутствуют:

- `durable restore failed`;
- `OperationalError`;
- `background startup failed`.

Доступность `/healthz` сама по себе для этого недостаточна.
