# Обратная связь по плану миграции: решения и обоснования

Ниже — постатейный разбор плана Replit с вердиктом по каждому пункту. Критерий принятия решений зафиксирован: **безопасная разработка — во главе угла**, целевая траектория — государственная система с аттестацией по требованиям ФСТЭК.

## Принимаем

**1. JSON API с префиксом `/api/*` (Задача 1 плана) — принимаем полностью.**
Почему: разделение данных и представления — архитектурно верный шаг независимо от судьбы фронтенда. API понадобится для интеграций в госверсии (обмен с 1С, выгрузки в вышестоящие системы), для любого будущего UI и для автоматизированного тестирования. Формализованные контракты запрос/ответ — это ровно то, что попадает в документацию при проектировании защиты: явные интерфейсы проще описывать в модели угроз, чем размазанную по шаблонам логику. Риск миграции низкий, бизнес-логика не затрагивается.

**2. Сессионная авторизация вместо JWT — принимаем.**
Почему: план прав, и это важно зафиксировать. Сессии на сервере отзываются мгновенно (уволили сотрудника — сессия убита), JWT живёт до истечения срока и требует инфраструктуры отзыва, которую все делают плохо. Для same-origin внутренней системы JWT — лишняя криптография без выгоды. Аргументация плана здесь совпадает с интересами ИБ.

**3. Неприкосновенность ядра (парсер, builder, БД, IMAP-логика, статические дашборды) — принимаем и фиксируем как принцип.**
Почему: проверенный код не трогаем без функциональной причины — каждое изменение аттестуемого кода это повторная проверка. Отдельно: статический HTML-дашборд без внешних библиотек — сохранить как архитектурный инвариант, он работает в закрытом контуре без интернета и не имеет JS-цепочки поставок.

**4. Таблица маршрутов и формат ошибок JSON — принимаем с дополнением.**
Дополнение: тексты ошибок наружу — только обобщённые («Внутренняя ошибка»), без stack trace и деталей СУБД; подробности — во внутренний журнал. Это прямое требование к ГИС: информативные ошибки — канал разведки для атакующего.

## Принимаем с изменением приоритета

**5. CSRF-защита — принимаем, но переносим из «рисков» в блокирующие требования, исполнение — первым.**
Почему: в плане это «спорный момент, можно добавить». Нет: сессионные cookie + изменяющие POST-запросы без CSRF-токена — эксплуатируемая уязвимость уже сегодня, в текущем MPA. Это единственный пункт плана, который закрывает реальную, а не эстетическую проблему, поэтому он идёт первым независимо от остального.

## Отклоняем

**6. React SPA (Задача 2 плана) — отклоняем.**
Почему, по пунктам:
- **Цепочка поставок.** React + Vite + Router + React Query + axios ≈ 300–500 транзитивных npm-пакетов. При безопасной разработке (ГОСТ Р 56939, анализ SBOM) каждый — объект учёта, сканирования и обоснования. Мы разменяли бы главный актив проекта — минимальную поверхность зависимостей — на удобство разработчика.
- **Не решает заявленную проблему.** Мотивация плана — «неповоротливость». Она серверная (синхронный парсинг в HTTP-запросе, один процесс), SPA её не лечит, см. пункт 8.
- **Компетенции сопровождения.** Госсистему будет сопровождать подрядчик/штат; Python-стек — один навык, Python+TypeScript+React — два, с разной скоростью устаревания. Это стоимость владения, а не разработки.
- **Отклоняем без предубеждения:** если через год появится функциональное требование, которое серверные шаблоны не тянут (сложные интерактивные формы, realtime), решение пересматривается — но уже с SBOM-процессом в бюджете.

**7. Отклонение HTMX в плане — отклоняем само отклонение.**
Почему: аргумент плана («не даёт чистых URL») фактически неверен — `hx-push-url` даёт. HTMX — это одна библиотека одним файлом, вендорится локально, работает в закрытом контуре. Если после серверных исправлений UI всё ещё будет ощущаться устаревшим — HTMX, а не React, является вариантом по умолчанию для нашего профиля рисков. Пока — остаёмся на Jinja.

## Требуем добавить (в плане отсутствует)

**8. Фоновая обработка загрузок + прогресс + gunicorn + вынос IMAP — добавить, приоритет сразу после CSRF.**
Почему: это и есть лечение «неповоротливости», ради которой писался план. Синхронный парсинг пачки xls внутри HTTP-запроса блокирует и пользователя, и соседей по процессу. Фоновая задача со статусом, 2–4 воркера gunicorn, IMAP в отдельном потоке/процессе — ноль новых внешних зависимостей, прямой эффект на отклик.

**9. Журналирование действий безопасности — добавить.**
Почему: входы/выходы, неудачные попытки, создание пользователей, смена ролей, загрузки файлов — с временем и адресом. Для будущей аттестации журнал регистрации событий обязателен, а начать накапливать практику дешевле сейчас, чем ретрофитить.

**10. Гигиена секретов и валидация загрузок — добавить.**
Почему: пароль IMAP не должен лежать в БД открытым текстом (шифрование на уровне приложения, ключ — в переменных окружения); загрузки — лимит размера, проверка расширений и содержимого (первые байты, а не имя файла), обработка zip с защитой от zip-bomb и path traversal (`../` в именах внутри архива). Всё это — типовые пункты проверки веб-приложений при аттестации.

## Итоговый порядок работ

1. CSRF (п. 5) → 2. Фон/воркеры/IMAP (п. 8) → 3. Журналирование и секреты (пп. 9–10) → 4. JSON API (п. 1, 4) → 5. UI — без изменений; вопрос HTMX открываем только при живой потребности после пп. 1–4.

Оценка: пункты 1–4 сопоставимы по трудоёмкости с Задачей 1 исходного плана (порядка недели), при этом Задача 2 (15–25 часов React) не выполняется вовсе — экономия прямая.

Этот текст можно отдавать Replit-агенту как есть — формулировки достаточно конкретны. Если нужно, разверну пункты 8–10 в техзадание с разбивкой по файлам проекта.
