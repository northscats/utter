# Справочник MAX Bot API и интеграции с АРМ

Переносимый справочник для реализации отдельного MAX-бота. Здесь описаны только контракты, подтверждённые текущим кодом проекта. Значения токенов, межсервисных секретов, адреса развёрнутых приложений и пользовательские данные намеренно не приводятся.

## 1. Границы документа

Текущая реализация реально использует только три метода MAX Bot API:

1. получение профиля бота;
2. long polling обновлений;
3. отправку сообщения пользователю или в чат.

Регистрация пользователя, администраторская модерация, подписки на объекты, хранение решений и обнаружение изменений объектов — это прикладная логика проектов АРМ и бота. Это не методы MAX API и в текущем проекте не реализовано как единый процесс.

## 2. Общие параметры MAX API

Базовый URL:

```text
https://platform-api.max.ru
```

Текущий клиент при каждом запросе передаёт токен одновременно двумя способами:

```http
Authorization: Bearer <MAX_BOT_TOKEN>
```

и query-параметром:

```text
access_token=<MAX_BOT_TOKEN>
```

Документ фиксирует фактическое поведение клиента, а не утверждает, что оба способа обязательны по официальной спецификации.

Для JSON-тела добавляется:

```http
Content-Type: application/json
```

Если HTTP-ответ MAX имеет статус вне диапазона `2xx`, текущий общий клиент читает текст ответа и формирует ошибку с HTTP-методом, путём, статусом и полученным текстом. При отправке сообщения ошибка журналируется, а вызывающему коду возвращается `null`.

## 3. Получение профиля бота

Используется при запуске сервиса. Ошибка этого запроса не останавливает polling.

```http
GET https://platform-api.max.ru/me?access_token=<MAX_BOT_TOKEN>
Authorization: Bearer <MAX_BOT_TOKEN>
```

Тело отсутствует.

Из ответа используются только:

```json
{
  "user_id": "<идентификатор бота>",
  "name": "<имя бота>"
}
```

- `user_id` преобразуется в строку и нужен, чтобы игнорировать сообщения, отправленные самим ботом.
- Если `name` отсутствует, интерфейс использует строку `MAX Bot`.
- Остальные поля ответа текущим сервисом не используются.

## 4. Long polling обновлений

Запрос:

```http
GET https://platform-api.max.ru/updates?timeout=20&limit=10&access_token=<MAX_BOT_TOKEN>[&marker=<MARKER>]
Authorization: Bearer <MAX_BOT_TOKEN>
```

Тело отсутствует.

Фактические query-параметры:

| Параметр | Значение в реализации | Назначение |
|---|---:|---|
| `timeout` | `20` | серверное ожидание обновлений |
| `limit` | `10` | максимальное число обновлений в запросе |
| `access_token` | токен бота | авторизация |
| `marker` | опциональное число | продолжение со следующей позиции |

Клиент дополнительно прерывает запрос через 25 секунд. `AbortError` при работающем сервисе считается штатным окончанием ожидания: цикл сразу начинает новый polling. Для других ошибок цикл ждёт 5 секунд перед повтором.

Ожидаемая часть ответа:

```json
{
  "updates": [],
  "marker": 123456
}
```

- `updates` при отсутствии трактуется как пустой массив.
- Если сервер вернул `marker`, он становится marker следующего запроса.
- Marker сохраняется в конфигурации проекта под ключом `max_bot_marker` и восстанавливается после перезапуска процесса, чтобы не обрабатывать старые обновления повторно.
- Код не вычисляет marker из `update_id`; он использует только `marker` верхнего уровня ответа.

### 4.1. Обычное сообщение

Обрабатывается update с:

```json
{
  "update_id": 123,
  "update_type": "message_created",
  "timestamp": 1710000000,
  "message": {
    "sender": {
      "user_id": 10001,
      "first_name": "Имя",
      "last_name": "Фамилия",
      "name": "Отображаемое имя",
      "is_bot": false
    },
    "recipient": {
      "chat_id": 20002,
      "chat_type": "dialog",
      "user_id": 10001
    },
    "body": {
      "text": "Текст сообщения",
      "mid": "message-id",
      "seq": 1,
      "attachments": []
    },
    "timestamp": 1710000000
  }
}
```

Фактические правила обработки:

- текст берётся из `message.body.text`, при отсутствии считается пустой строкой и обрезается по краям;
- вложения берутся только из `message.body.attachments`;
- сообщение от `sender.user_id`, совпадающего с `user_id` бота из `/me`, игнорируется;
- обычные сообщения обрабатываются только при `recipient.chat_type === "dialog"`;
- команда `/chatid` является исключением и допускается также в группе/канале;
- имя отправителя выбирается в порядке `sender.name`, затем `first_name + last_name`, затем `sender.user_id`.

### 4.2. Идентификаторы личного диалога и группы

Внутри текущего сервиса:

- личный диалог обозначается как `u:<sender.user_id>`;
- группа или другой общий чат обозначается строковым `recipient.chat_id`.

Префикс `u:` — внутреннее соглашение приложения, а не значение, отправляемое в MAX API. Метод отправки преобразует его в query-параметр `user_id`.

Для личного диалога:

```text
u:10001  →  POST /messages?...&user_id=10001
```

Для группы:

```text
20002    →  POST /messages?...&chat_id=20002
```

### 4.3. Callback от inline-кнопки

Обрабатывается update с:

```json
{
  "update_type": "message_callback",
  "callback": {
    "callback_id": "optional-callback-id",
    "id": "optional-id",
    "user": {
      "user_id": 10001,
      "first_name": "Имя",
      "last_name": "Фамилия",
      "name": "Отображаемое имя"
    },
    "chat_id": 20002,
    "message": {
      "mid": "message-id"
    },
    "payload": "cmd:start",
    "timestamp": 1710000000
  }
}
```

Текущий обработчик использует только:

- `callback.user.user_id`;
- поля имени пользователя;
- `callback.payload`.

Для ответа callback-пользователю обработчик строит внутренний адрес `u:<callback.user.user_id>`. Поля `callback_id`, `id`, `chat_id` и `message.mid` описаны типом, но текущей обработкой не используются.

Отдельный endpoint подтверждения callback не вызывается. В реализации прямо зафиксировано, что endpoint `/answers` не используется и подтверждение не требуется. Нельзя придумывать такой запрос при переносе.

Неизвестные `update_type` только журналируются.

## 5. Отправка сообщений

### 5.1. Пользователю

```http
POST https://platform-api.max.ru/messages?access_token=<MAX_BOT_TOKEN>&user_id=<MAX_USER_ID>
Authorization: Bearer <MAX_BOT_TOKEN>
Content-Type: application/json

{
  "text": "Привет"
}
```

### 5.2. В чат

```http
POST https://platform-api.max.ru/messages?access_token=<MAX_BOT_TOKEN>&chat_id=<MAX_CHAT_ID>
Authorization: Bearer <MAX_BOT_TOKEN>
Content-Type: application/json

{
  "text": "Сообщение в группу"
}
```

`user_id` или `chat_id` передаются именно в query string. В исходящем JSON нет обёрток `recipient` и `body`; такие поля относятся к входящему update.

Неправильный для этой реализации формат:

```json
{
  "recipient": { "chat_id": 20002 },
  "body": { "text": "Сообщение" }
}
```

### 5.3. Inline-клавиатура

Подтверждённое тело:

```json
{
  "text": "Выберите действие",
  "attachments": [
    {
      "type": "inline_keyboard",
      "payload": {
        "buttons": [
          [
            {
              "type": "callback",
              "text": "Одобрить",
              "payload": "registration:approve:request-id"
            },
            {
              "type": "callback",
              "text": "Отклонить",
              "payload": "registration:reject:request-id"
            }
          ]
        ]
      }
    }
  ]
}
```

`buttons` — массив рядов, каждый ряд — массив кнопок. Текущий помощник принимает для кнопки только `text` и `payload`, а при сборке запроса добавляет `type: "callback"`.

Пример payload выше показывает, как можно кодировать прикладное действие. Значения `registration:*` не являются существующим контрактом текущего проекта: схему payload, проверку прав и хранение решения надо реализовать отдельно.

### 5.4. Вложения

Подтверждённая минимальная форма:

```json
{
  "type": "image",
  "payload": {
    "token": "<MEDIA_TOKEN>"
  }
}
```

или:

```json
{
  "type": "image",
  "payload": {
    "url": "https://example.invalid/media"
  }
}
```

Тип вложения в коде является строкой; фактически текущий сценарий принимает и пересылает фото и видео из `message.body.attachments`. При пересылке сервис по возможности сохраняет исходные объекты вложений целиком, включая их `type` и `payload`. Если остались только нормализованные поля, он собирает вложение из `type` и одного из `payload.token` или `payload.url`.

Inline-клавиатура добавляется в тот же массив `attachments`, поэтому сообщение может содержать медиа и клавиатуру одновременно.

Текущий код не загружает файлы в MAX самостоятельно и не документирует upload endpoint. Такой endpoint нельзя выводить из приведённой структуры.

### 5.5. Ответ и ошибки отправки

Идентификатор отправленного сообщения ищется последовательно:

1. `response.message_id`;
2. `response.message.body.mid`;
3. `response.message.mid`.

Если ни одно поле не найдено, отправка уже получила успешный HTTP-ответ, но метод возвращает `null` и журналирует отсутствие `mid`. При HTTP/сетевой ошибке метод также возвращает `null`.

## 6. Внутренний API: бот-проект → АРМ

### 6.1. Поиск пользователя по `link_code`

```http
GET <ARM_BASE_URL>/api/bot/user?code=<LINK_CODE>
X-Bot-Key: <ARM_INTEGRATION_SECRET>
```

Тело отсутствует.

Сравнение `X-Bot-Key` выполняется с секретом, сохранённым в конфигурации АРМ. Это отдельный межсервисный секрет, не MAX Bot Token.

Успешный ответ:

```json
{
  "id": "<arm-user-id>",
  "username": "<username>",
  "email": "<email>",
  "linkCode": "XXXX-XXXX-XXXX"
}
```

Статусы ошибок:

| HTTP | Ответ | Условие |
|---:|---|---|
| `400` | `{"message":"code is required"}` | query-параметр `code` отсутствует или пуст |
| `401` | `{"message":"Unauthorized"}` | секрет не настроен или `X-Bot-Key` не совпал |
| `404` | `{"message":"Пользователь не найден"}` | точного совпадения `link_code` нет |
| `500` | `{"message":"Ошибка сервера"}` | внутренняя ошибка |

Поиск выполняется по точному значению `users.link_code`. Поле уникально. Текущий генератор создаёт 12 символов из алфавита без неоднозначных `0/O/1/I` в формате `XXXX-XXXX-XXXX`.

Этот endpoint подтверждает связь с пользователем АРМ, но сам по себе:

- не сохраняет MAX `user_id`;
- не создаёт заявку на регистрацию;
- не меняет статус пользователя;
- не запускает модерацию.

Эти данные и переходы состояний должны храниться в бот-проекте или в отдельно спроектированном API АРМ.

## 7. Внутренний API: АРМ → бот-проект

АРМ отправляет уведомление:

```http
POST <BOT_PROJECT_URL>/api/notify
X-Bot-Key: <ARM_INTEGRATION_SECRET>
Content-Type: application/json
```

Фактически поддерживаемые текущим вызывающим кодом поля:

```json
{
  "type": "task_assigned",
  "toArmUserId": "<arm-user-id>",
  "fromName": "Имя отправителя",
  "period": "Период",
  "comment": "Комментарий",
  "title": "Заголовок",
  "courseTitle": "Название курса",
  "message": "Текст",
  "idempotencyKey": "стабильный-ключ",
  "deepLink": "/relative/path"
}
```

Обязательны в TypeScript-контракте:

- `type`;
- `toArmUserId`.

Остальные поля опциональны. Допустимые `type`, которые формирует текущий АРМ:

```text
turv_submitted
turv_approved
turv_rejected
turv_reminder
task_assigned
task_co_assigned
training_course_assigned
kpi_assigned
kpi_revision
```

Таймаут исходящего запроса — 5 секунд.

Семантика ответа бот-проекта:

- любой HTTP-статус вне `2xx` означает `failed`; до 500 символов тела включаются в диагностическую причину;
- успешный JSON с `delivered: false` означает `skipped`;
- успешный JSON с `skipped: true` означает `skipped`;
- причина берётся из `reason`, по умолчанию — `recipient_not_linked`;
- любой другой успешный ответ, включая пустое или не-JSON тело, означает `sent`.

Перед вызовом АРМ также проверяет локальную настройку типа уведомления пользователя. Отключённый тип даёт `skipped` с причиной `disabled_by_user`. Отсутствующая конфигурация URL или секрета даёт `skipped` с причиной `bot_not_configured`.

Контракт принимающего `/api/notify` должен быть реализован в отдельном бот-проекте. В этом репозитории подтверждён только вызывающий контракт АРМ; нельзя предполагать дополнительные поля или статусы получателя.

## 8. Что уже можно использовать в целевом сценарии

Подтверждённые примитивы:

- `/me` — проверить токен и получить идентификатор бота;
- `/updates` — получать личные сообщения и callback на кнопки;
- `/messages?user_id=...` — отвечать пользователю или уведомлять модератора;
- `/messages?chat_id=...` — отправлять сообщение в настроенную группу;
- inline-кнопки с callback payload — показать модератору действия;
- `GET /api/bot/user?code=...` — найти пользователя АРМ по коду привязки;
- `POST <BOT_PROJECT_URL>/api/notify` — принять событие от АРМ и доставить его связанному MAX-пользователю.

## 9. Что требуется реализовать отдельно

Следующее отсутствует как готовый сквозной процесс и не должно выдаваться за MAX API:

1. **Заявка на регистрацию:** хранение MAX `user_id`, кода привязки, времени и статуса заявки.
2. **Администраторская модерация:** определение списка администраторов, отправка им карточки, проверка полномочий callback-пользователя, атомарное сохранение решения.
3. **Защита callback:** непротиворечивые payload, проверка идентификатора заявки, повторных кликов и уже принятого решения.
4. **Связь АРМ ↔ MAX:** постоянное соответствие `toArmUserId` и MAX `user_id`; endpoint поиска по коду это соответствие не хранит.
5. **Подписки на объекты:** таблицы подписок, права на объект, добавление/удаление подписки и пользовательские настройки.
6. **Обнаружение изменений:** источник событий или плановый опрос, сравнение версий/полей, дедупликация и формирование `idempotencyKey`.
7. **Доставка и повторы:** обработка недоступности MAX, повторные попытки и журнал результата, если этого требует бизнес-сценарий.

## 10. Доказательная база в репозитории

Контракты сверены со следующими исходниками:

- `server/maxBot.ts`:
  - `MAX_API`, типы update и вложений;
  - запуск через `GET /me`;
  - общий HTTP-клиент и двойная передача токена;
  - `sendMessage`, адресация, inline-клавиатура и разбор `mid`;
  - polling `/updates`, marker, таймауты и ошибки;
  - обработка `message_created` и `message_callback`;
  - приём и пересылка медиа.
- `server/routes.ts`:
  - `GET /api/bot/user`;
  - настройки межсервисной интеграции;
  - исходящий `POST <BOT_PROJECT_URL>/api/notify` и семантика результата.
- `server/storage.ts`:
  - точный поиск пользователя по `link_code`;
  - формат генерации кода.
- `shared/schema.ts`:
  - уникальное поле `users.link_code`;
  - существующие таблицы маршрутизации чатов и сохранённых пользователем УИН.
- `server/bootstrap.ts`:
  - создание `users.link_code` и заполнение кодов для существующих пользователей.
- `client/src/pages/BotIntegrationPage.tsx`:
  - назначение `ARM_BASE_URL`, `X-Bot-Key` и URL отдельного бот-проекта.
- `.agents/memory/max-bot-api-send.md` и `.agents/memory/bot-link-code.md`:
  - зафиксированные проверенные особенности формата отправки и наименования кода привязки.

## 11. Контроль безопасности при переносе

- Хранить MAX Bot Token и `X-Bot-Key` только как секреты окружения или в защищённой конфигурации.
- Не использовать один и тот же секрет для MAX и межсервисной авторизации.
- Не журналировать токены, коды привязки, содержимое персональных уведомлений и полные ответы с чувствительными данными.
- Не копировать значения настроек из текущего окружения.
- Не добавлять методы MAX, которые не подтверждены исходниками этого справочника.
