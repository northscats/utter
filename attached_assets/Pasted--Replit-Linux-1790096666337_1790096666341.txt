Я разрабатываю систему «Аналитика РСО» на Replit и периодически деплою её в закрытый контур на Linux-сервере в Docker-контейнере. Есть проблемы:

Система долго загружается при старте

Периодически происходят сбои (причины неизвестны)

Агенты Replit не видят, что именно происходит на проде — нет телеметрии

DevOps-доступ ограничен, диагностика вручную затруднена

На сервере действуют политики безопасности, фаервол, антивирус, возможны сетевые ограничения

Внешняя телеметрия (Sentry, Grafana Cloud и т.п.) недопустима — только локальные логи

Задача
Спроектировать и реализовать лёгкую систему логирования и диагностики, которая:

Пишет логи на всех этапах жизненного цикла: сборка Docker-образа → старт контейнера → миграции/инициализация → работа фронтенда → работа бэкенда → фоновые задачи → graceful shutdown → падение.

Позволяет одним действием (скриптом/командой) собрать полный диагностический бандл и скачать его, чтобы передать в Replit для анализа.

Потребляет минимум CPU/RAM/диска (низкий overhead, ротация, лимиты).

Работает полностью offline, без внешних сервисов и без исходящих соединений.

Требования к реализации
1. Структура логов
Единая директория ./logs/ (монтируется как volume), подкаталоги по компонентам:

logs/app/ — бэкенд

logs/frontend/ — фронт (ошибки браузера, если применимо)

logs/build/ — этап сборки образа

logs/startup/ — инициализация контейнера, entrypoint, миграции

logs/infra/ — системные метрики, ошибки Docker/OS

logs/crashes/ — дампы при падениях

Формат: JSON Lines (по одной записи в строке) со схемой:

json
{
  "ts": "ISO8601",
  "level": "debug|info|warn|error|fatal",
  "component": "backend|frontend|startup|build",
  "module": "auth",
  "msg": "...",
  "ctx": { "...произвольные поля..." },
  "req_id": "uuid",
  "duration_ms": 123
}
Ротация: RotatingFileHandler/logrotate — например 10 МБ × 5 файлов на компонент. Сжатие gzip старых.

2. Логирование на этапах развёртывания
Dockerfile / build stage: логи сборки в logs/build/build.log (tee вывода установщика зависимостей).

Entrypoint контейнера (docker-entrypoint.sh):

отметка времени старта, версия образа, git-commit

проверка доступности зависимостей (БД, кэш, файловые пути)

логирование миграций с таймингом каждой

фиксация переменных окружения (без секретов, только ключи и маскированные значения)

запись logs/startup/startup.json — тайминги этапов

Healthcheck: эндпоинт /healthz + /readyz, пишущий в logs/app/health.log при неуспехе.

3. Логирование бэкенда
Middleware: request_id, метод, путь, статус, длительность, IP (маскированный), user-agent.

Логи медленных запросов (> N мс) отдельно: logs/app/slow.log.

Полный stack trace при исключениях.

Логи фоновых задач, ретраев, таймаутов внешних вызовов.

Опционально: sampling для info (не логировать 100% успешных запросов — только сэмпл или агрегаты), error/warn — 100%.

4. Логирование фронтенда
Глобальные перехватчики window.onerror, unhandledrejection.

Отправка ошибок на бэкенд эндпоинт /api/logs/frontend (только в закрытом контуре, без внешних сервисов).

Лог медленных загрузок, failed fetch/XHR.

Не логировать PII и токены — фильтр по ключам.

5. Диагностический бандл (collect-diagnostics.sh)
Один скрипт, который собирает:

все логи из ./logs/

docker inspect контейнера

docker stats --no-stream

docker logs --tail=10000

метрики ОС: free -m, df -h, uptime, top -b -n1, dmesg | tail

статус портов: ss -tulpn

проверку диска, inode

версии: OS, Docker, runtime приложения

checksum манифест всех файлов

архивирует в diagnostics-YYYYMMDD-HHMMSS.tar.gz с паролем (опционально), кладёт в ./logs/exports/, и не отправляет никуда — только локально для скачивания.

6. Низкое потребление ресурсов
Асинхронная запись (буфер + фоновый writer), чтобы не блокировать HTTP.

Уровень логирования настраивается через LOG_LEVEL (по умолчанию info, на проде можно warn).

Sampling и rate limiting для шумных сообщений (не более X одинаковых в минуту).

Никаких зависимостей типа ELK/Loki/Prometheus — только stdlib + 1-2 лёгкие библиотеки.

Лимит на размер logs/ (например 500 МБ), автоочистка старых.

7. Безопасность и совместимость с закрытым контуром
Никаких исходящих соединений — не звонить ни в Sentry, ни в любой внешний API.

Маскирование секретов: regex-фильтр по password|token|secret|api_key|authorization.

Права на файлы логов 0640, владелец — пользователь контейнера.

Работа при отсутствии интернета и без DNS.

Не требовать root в рантайме.

Совместимость с антивирусом: обычные текстовые/JSON-файлы, без обфускации.

8. Документация
LOGGING.md: структура логов, схема JSON, как включить debug, как собрать бандл, как передать в Replit, ограничения (что НЕ логируется — PII, секреты).

Скрипт tail.sh — удобный просмотр последнего по всем компонентам.

Что мне нужно от тебя (агент Replit)
Предложи структуру файлов и модулей.

Сгенерируй код:

модуль логирования бэкенда (async writer, rotation, JSON-форматтер, middleware);

docker-entrypoint.sh с логами старта;

фрагмент Dockerfile с монтированием logs/ и передачей логов сборки;

фронтенд-перехватчик ошибок + эндпоинт /api/logs/frontend;

collect-diagnostics.sh — самодостаточный bash без внешних зависимостей (кроме coreutils/docker);

конфиг logrotate для хоста;

LOGGING.md.

Учти, что изначально неизвестны точные причины сбоя и медленного старта — поэтому система должна помочь найти причину: логировать тайминги каждого этапа, показывать где «залипает» старт, сохранять ошибки с полным контекстом.

Не тяни тяжёлые библиотеки. Приоритет — stdlib языка проекта.

Спроси у меня уточнения, если нужны детали стека (Python/Node/Go?), но по умолчанию сделай так, чтобы решение было переносимым и легко адаптировалось к любому бэкенду.

Критерий готовности
Я могу одной командой собрать diagnostics-*.tar.gz и скачать его → загрузить в Replit → агент видит полную картину: тайминги старта, ошибки фронта и бэка, состояние ОС и контейнера.

Overhead логирования ≤ 1-2% CPU и ≤ 50 МБ RAM.

Ни одного исходящего сетевого соединения от системы логирования.

Секреты и PII не попадают в логи (проверка тестом).
