# Интеграция DaData для геокодирования при импорте XLS/XLSX

## 1. Назначение и границы документа

Этот документ описывает фактическую реализацию DaData в системе: от загрузки Excel-файла до появления координат, ФИАС ID, точности и статуса у импортированных объектов. Инструкция предназначена для разработчика, который переносит такой сценарий в другую систему.

Описаны два режима:

1. **По адресу** — запрос к DaData `suggest/address`, получение координат и ФИАС ID.
2. **По ФИАС ID** — запрос к DaData `findById/address`, получение адреса и координат.

Основной предмет нестандартной транспортной настройки — массовое **адресное** геокодирование через `suggest/address`. В текущем коде режим по ФИАС реализован отдельным циклом и не использует настраиваемые `pseudoSingle`, `rps`, `concurrency`, `jitterMs`, `retries`, `backoffMs` и `timeoutMs`. Это различие нельзя скрывать при переносе.

Обратное геокодирование, AI-инструменты и общий поиск по ФИАС здесь не рассматриваются, кроме кратких пояснений архитектуры.

## 2. Что обязательно перенести, а что является локальной архитектурой

### Обязательные элементы совместимости

- запросы к DaData выполняются только сервером;
- API-ключ никогда не отправляется в браузер и не записывается в Excel;
- для адреса используется HTTPS `POST` на `suggest/address`;
- заголовок авторизации имеет вид `Authorization: Token <API_KEY>`;
- отправляется JSON и ожидается JSON;
- берётся первый элемент `suggestions`;
- координаты `geo_lat` и `geo_lon` проверяются на наличие и преобразуемость в числа;
- пустой `suggestions`, отсутствие координат и некорректные координаты считаются корректно обработанным результатом «не найдено», а не успешной геометрией;
- массовый поток ограничивает общий RPS, поддерживает timeout, повторяемые ошибки и отмену;
- результат строки хранится независимо, чтобы неудачные строки можно было повторить;
- при нестабильных соединениях должен быть доступен режим без повторного использования keep-alive-сокета.

### Детали именно текущего приложения

- сущности «редактируемый слой», «объект слоя» и «загрузка»;
- внутренние HTTP API `/api/...`;
- временная точка `[0, 0]` до завершения геокодирования;
- chunk по 200 объектов и пакетные обновления БД;
- панель загрузок и SSE-механизм её обновления;
- названия полей `geocoding_status`, `geocoded_address` и т. п.;
- хранение настроек в `app_settings`;
- права `ADMIN_SYSTEM`, `LAYERS_CREATE`, `LAYERS_EDIT`.

В другой системе эти детали можно заменить очередью заданий, таблицей импорта или иным хранилищем, сохранив обязательный контракт выше.

## 3. Полный путь данных

### 3.1. Настройка провайдера и секрета

Администратор:

1. выбирает провайдер `dadata`;
2. сохраняет API-ключ DaData;
3. при необходимости настраивает транспорт массового геокодирования;
4. запускает одиночный тест на контрольном адресе.

Текущая система сначала ищет ключ в серверной настройке `geocode_dadata_api_key`, затем использует серверную переменную окружения `DADATA_API_KEY`. Значение ключа не возвращается клиенту: интерфейс получает только признак наличия и маску последних символов.

Для адресной колонки применяется выбранный глобальный провайдер. Для колонки ФИАС DaData выбирается принудительно независимо от глобального провайдера.

Настройки транспорта читаются заново при каждом вызове адресного batch, фактически для каждого серверного chunk. Поэтому изменения применяются без перезапуска процесса к следующим пакетам.

### 3.2. Загрузка и разбор XLS/XLSX

Сервер принимает только `.xls` и `.xlsx`, с лимитом 200 МБ. Для пользователей без роли администратора дополнительно действует ограничение 50 МБ. Большие файлы могут загружаться частями, но после сборки проходят тот же разбор.

Фактический разбор:

1. ExcelJS открывает книгу.
2. Используется первый лист.
3. Первая строка считается заголовком.
4. Строки данных начинаются со второй строки.
5. Полностью пустые строки не учитываются.
6. Для формулы берётся вычисленный `result`, для rich text — `text`.
7. Клиенту возвращаются имена колонок, до 100 строк предпросмотра и общее число непустых строк.
8. Полный файл остаётся во временной серверной parse-сессии на 30 минут; при подтверждении импорта он читается повторно и удаляется.

Система автоматически распознаёт типовые названия широты, долготы и GeoJSON. Адресную и ФИАС-колонку пользователь назначает явно.

### 3.3. Выбор режима

В интерфейсе роли адреса, ФИАС, пары широта/долгота и GeoJSON взаимоисключающие. Для данного документа важны:

- **«Адрес (геокодер)»** — значение строки отправляется в `suggest/address`;
- **«ФИАС ID (DaData)»** — значение отправляется в `findById/address`.

Можно выбрать не более одной колонки каждого специального типа. Остальные колонки сохраняются как атрибуты либо исключаются.

### 3.4. Создание строк и запуск фоновой работы

При адресном или ФИАС-режиме слой и все объекты создаются до вызовов DaData:

- начальная геометрия — техническая точка `[0, 0]`;
- `geocoding_status = "pending"`;
- исходный адрес или ФИАС ID сохраняется в выбранной колонке;
- создаётся запись фоновой загрузки со статусом `processing`;
- устанавливается защита от двух одновременных заданий для одного слоя;
- клиент сразу получает `201`, идентификаторы слоя и задания;
- геокодирование продолжается в фоне.

Важно: `[0, 0]` — локальная временная заглушка, а не результат DaData. В другой системе предпочтительно хранить геометрию как `NULL`, если модель данных это допускает.

### 3.5. Обработка chunk и прогресс

Фоновый процесс:

1. считает объекты в статусе `pending`;
2. получает только их идентификаторы;
3. обрабатывает их chunk по 200;
4. загружает полные объекты текущего chunk;
5. вызывает адресный или ФИАС batch;
6. накапливает успешные обновления координат и неуспешные обновления свойств;
7. записывает обе группы пакетно;
8. обновляет прогресс.

Пользователь видит подпись вида `Геокодирование: 400 / 1200`. Запись прогресса в БД выполняется примерно каждые 500 объектов и на последнем chunk; оперативная подпись также держится в памяти. По окончании отображается число успешно геокодированных объектов.

## 4. Точный HTTP-контракт DaData для адреса

### 4.1. Запрос

```http
POST https://suggestions.dadata.ru/suggestions/api/4_1/rs/suggest/address
Content-Type: application/json
Accept: application/json
Authorization: Token <DADATA_API_KEY>
Connection: close

{
  "query": "Московская область, г. Примерск, ул. Центральная, д. 10",
  "count": 1
}
```

`Connection: close` отправляется только при включённом `pseudoSingle`. Без него заголовок не добавляется.

Реальный ключ вместо `<DADATA_API_KEY>` должен подставляться сервером из защищённого хранилища. Не помещайте его в исходный код, клиентский bundle, журналы или примеры документации.

### 4.2. Обезличенный пример ответа

```json
{
  "suggestions": [
    {
      "value": "Московская обл, г Примерск, ул Центральная, д 10",
      "unrestricted_value": "Московская обл, г Примерск, ул Центральная, д 10",
      "data": {
        "fias_id": "00000000-0000-0000-0000-000000000000",
        "fias_level": "8",
        "geo_lat": "55.123456",
        "geo_lon": "37.654321"
      }
    }
  ]
}
```

Текущая система использует только:

| Поле ответа | Назначение |
|---|---|
| `suggestions[0]` | первый и единственный запрошенный вариант |
| `suggestions[0].value` | нормализованный адрес |
| `suggestions[0].data.geo_lat` | широта, строка → число |
| `suggestions[0].data.geo_lon` | долгота, строка → число |
| `suggestions[0].data.fias_id` | ФИАС ID, если есть |
| `suggestions[0].data.fias_level` | уровень ФИАС для признака точности |

Нормализованный результат:

```text
lat              = parseFloat(data.geo_lat)
lon              = parseFloat(data.geo_lon)
formattedAddress = suggestion.value, иначе исходный адрес
fiasId           = data.fias_id, если непустой
precision        = "fias_level_" + data.fias_level, иначе "unknown"
```

Координаты сохраняются в GeoJSON-порядке `[lon, lat]`.

### 4.3. Валидация ответа

Алгоритм не создаёт успешный результат, если:

- `suggestions` отсутствует или пуст;
- у первого варианта отсутствует `geo_lat` или `geo_lon`;
- `parseFloat` даёт `NaN`.

В этих случаях строка получает `result = null`, затем статус `failed` и сообщение «Адрес не найден» (либо более конкретную ошибку batch).

Текущий код проверяет числовой формат, но после ответа DaData отдельно не ограничивает диапазоны широты и долготы. При переносе разумно дополнительно проверять `-90…90` и `-180…180`; это усиление, а не описание действующего поведения.

## 5. Контракт режима по ФИАС

```http
POST https://suggestions.dadata.ru/suggestions/api/4_1/rs/findById/address
Content-Type: application/json
Accept: application/json
Authorization: Token <DADATA_API_KEY>

{
  "query": "00000000-0000-0000-0000-000000000000"
}
```

Разбор первого suggestion и координат аналогичен адресному режиму. Отличия нормализации:

- `formattedAddress = suggestion.value`, иначе исходный ФИАС ID;
- `fiasId = data.fias_id`, иначе исходный ФИАС ID;
- `precision = "fias_level_<уровень>"`, а при отсутствии уровня — `"fias"`.

Фактические параметры этого цикла:

- последовательно;
- пауза между элементами `ceil(1000 / 20) = 50` мс;
- timeout 15 000 мс;
- для `429` — до 3 повторов с задержками 2, 4 и 6 секунд;
- после исчерпания повторов cooldown 5, 10, … до 30 секунд;
- после пяти последовательных timeout — пауза 30 секунд;
- после отдельного timeout неуспешная строка фиксируется и добавляется пауза 3 секунды.

В текущем коде ФИАС-запрос выполняется обычным `fetch`: псевдо-одиночный режим и пользовательские настройки адресного транспорта к нему не применяются.

## 6. Устойчивая адресная пакетная обработка

### 6.1. Значения по умолчанию и допустимые диапазоны

| Параметр | По умолчанию | Допустимо | Смысл |
|---|---:|---:|---|
| `pseudoSingle` | `false` | boolean | новое соединение на запрос |
| `rps` | `20` | 1–50 | общий целевой темп запросов |
| `concurrency` | `1` | 1–10 | число параллельных workers |
| `jitterMs` | `0` | 0–10 000 | случайная добавка к паузам |
| `timeoutMs` | `15 000` | 1 000–120 000 | timeout одного HTTP-запроса |
| `retries` | `3` | 0–10 | повторы transient-ошибки |
| `backoffMs` | `2 000` | 0–60 000 | база линейного backoff |

Это значения схемы и фактические серверные defaults. Текст интерфейса в одном месте упоминает RPS 10, но код и схема используют **20**; для воспроизведения следует ориентироваться на код.

### 6.2. Ограничение общего RPS

При последовательной обработке:

```text
baseDelayMs = ceil(1000 / rps)
delay       = baseDelayMs + random(0 .. jitterMs-1)
```

При `concurrency > 1` адреса распределяются по workers round-robin. Каждый worker выдерживает:

```text
perWorkerDelayMs = concurrency * ceil(1000 / rps)
```

Поэтому суммарный номинальный RPS не умножается на число workers. Например, `rps=10`, `concurrency=2`: каждый worker ждёт 200 мс, а общий поток остаётся около 10 запросов/с.

Jitter добавляется независимо к паузе каждого worker и только уменьшает фактический RPS. Начальные запросы workers стартуют почти одновременно, поэтому это ограничитель среднего темпа, а не строгий глобальный token bucket. Для систем с жёсткой квотой лучше реализовать общий rate limiter.

### 6.3. Псевдо-одиночный режим

Проблемная нагрузка отличалась от успешного одиночного теста повторным использованием HTTP keep-alive-соединений. Рабочий обходной режим приближает каждый batch-запрос к одиночному:

- заголовок `Connection: close`;
- Undici Agent с `pipelining: 0`;
- `keepAliveTimeout: 1`;
- `keepAliveMaxTimeout: 1`.

Практический эффект — свежий сокет для каждого запроса вместо повторного использования соединения, которое удалённая сторона или промежуточный прокси может уже считать закрытым.

Цена режима:

- дополнительный TCP/TLS handshake;
- выше задержка и нагрузка на сеть;
- ниже возможная пропускная способность.

Поэтому это отключаемый режим совместимости, а не универсальная рекомендация для любого окружения.

### 6.4. Timeout и классификация ошибок

Timeout адресного запроса задаётся `timeoutMs`. Пользовательская отмена передаётся родительским `AbortSignal` и отличается от внутреннего timeout.

Transient network error распознаётся по кодам или сообщениям:

- `ECONNRESET`;
- `ECONNREFUSED`;
- `ETIMEDOUT`;
- `EPIPE`;
- `UND_ERR_SOCKET`;
- `UND_ERR_CONNECT_TIMEOUT`;
- `socket hang up`;
- `other side closed`;
- `terminated`;
- сообщения с `ECONNRESET` или `UND_ERR`.

Повторяемыми считаются:

- transient network error;
- timeout;
- HTTP `429`.

HTTP `401` и `403` превращаются в ошибку авторизации и прерывают batch на уровне вызывающего фонового процесса. Прочие HTTP-ошибки не повторяются автоматически.

### 6.5. Повторы и backoff

Для попытки с номером `n`, начиная с 1:

```text
retryDelay = backoffMs * n
```

Для сетевой ошибки в последовательном режиме и для всех повторяемых ошибок в параллельном helper добавляется `random(0 .. jitterMs-1)`. Последовательная ветка timeout и `429` jitter к retry не добавляет.

При defaults повторы происходят примерно через 2, 4 и 6 секунд.

Последовательная ветка дополнительно:

- после пяти исчерпанных timeout подряд ждёт 30 секунд;
- после каждого исчерпанного timeout ждёт ещё 3 секунды;
- после исчерпанного `429` задаёт cooldown `min(30 секунд, 5 секунд × число последовательных 429)`.

В параллельной ветке retry выполняется независимо внутри worker. Отдельного общего cooldown после исчерпания retries там нет: строка получает ошибку. Это ещё одно фактическое отличие режимов.

## 7. Почему одиночный тест проходит, а Excel-пакет падает

Одиночный тест проверяет ключ, endpoint и один адрес. Он не воспроизводит:

- длительное повторное использование сокета;
- серию запросов на границе квоты;
- параллельные запросы;
- накопление закрытых удалённой стороной keep-alive-соединений;
- кратковременные сетевые сбои на длинном задании;
- неоднородные адреса и ответы без координат.

Поэтому «тест соединения успешен» не доказывает готовность к файлу на тысячи строк.

Характерные причины:

- **`ECONNRESET` / `socket hang up`** — сервер, балансировщик или прокси закрыл переиспользуемый сокет;
- **timeout** — медленный ответ, перегрузка, сетевой путь или слишком агрессивная параллельность;
- **429** — фактический темп выше разрешённого тарифом/окружением либо запросы идут ещё из других процессов;
- успешный HTTP 200 без координат — DaData нашла вариант недостаточной гранулярности или не вернула геокоординаты.

## 8. Матрица диагностики

| Симптом | Вероятная причина | Рекомендуемое действие |
|---|---|---|
| `401` или `403` | неверный, отозванный или неподходящий ключ | остановить batch; проверить серверный secret и доступ продукта DaData; не повторять запросы автоматически |
| одиночный тест успешен, пакет даёт `ECONNRESET` / `socket hang up` | нестабильное keep-alive reuse | включить `pseudoSingle`; оставить `concurrency=1`; повторить средний тест |
| редкие `ECONNRESET` | краткий сетевой сбой | оставить 3 retries и линейный backoff; добавить небольшой jitter |
| много timeout подряд | перегрузка/медленная сеть/высокая concurrency | сначала снизить concurrency до 1, затем RPS; только потом осторожно увеличить timeout |
| `429` | превышен лимит или есть другие отправители | снизить общий RPS; проверить другие экземпляры/задания; сохранить backoff и cooldown |
| `suggestions: []` | адрес не распознан | пометить строку failed; исправить/дополнить адрес; повторить только ошибки |
| suggestion есть, координат нет | недостаточная точность данных | не сохранять `[0,0]` как успех; оставить failed и проверить исходный адрес/ФИАС уровень |
| координаты не числа | повреждённый/неожиданный ответ | failed, сохранить безопасное диагностическое сообщение; не создавать геометрию |
| пакет остановился на ошибке API | batch-level auth/необработанная ошибка | исправить причину; оставшиеся `pending` не переводить в failed; продолжить повторным запуском |
| отменено пользователем | сработал AbortSignal | остановить новые запросы; явно зафиксировать отмену; определить политику повторного запуска |

Не записывайте полный `Authorization` и API-ключ в логи. Адреса также могут быть чувствительными; в текущих debug-строках они обрезаются, а в сторонней системе следует определить срок хранения и доступ.

## 9. Безопасная последовательность подбора транспорта

1. Проверить один адрес при `concurrency=1`.
2. Запустить файл на 10–20 репрезентативных адресов.
3. При reset/hang up включить `pseudoSingle`, не меняя одновременно остальные параметры.
4. Для первого массового испытания использовать `concurrency=1` и консервативный RPS, соответствующий фактическому тарифу DaData и общему числу экземпляров приложения.
5. При `429` снижать RPS; увеличение timeout проблему квоты не решает.
6. При timeout сначала снизить concurrency/RPS, затем проверить сеть, и только потом повышать timeout.
7. При редких синхронных сбоях добавить jitter, например 100–500 мс.
8. Увеличивать concurrency по одному шагу, каждый раз проводя длинный тест.
9. Не повышать одновременно RPS и concurrency: иначе невозможно понять источник регрессии.
10. После подбора провести длительный тест объёмом, близким к рабочему, и проверить долю failed, 429, timeout и reset.

Defaults системы — это зафиксированное текущее поведение, а не обещание соответствия любому тарифу DaData. Лимит следует согласовать с договором и учитывать суммарную нагрузку всех процессов.

## 10. Обработка исходов и сохранение

### Успех

Для адресной строки сохраняются:

```text
coordinates        = [lon, lat]
geocoding_status   = "geocoded"
geocoded_address   = formattedAddress
geocode_precision  = precision
fias_id            = fiasId, только если DaData его вернула
```

Для ФИАС-строки `fias_id` сохраняется из ответа, а при отсутствии — исходное значение.

### Пустой или неполный результат

Сохраняются:

```text
geocoding_status = "failed"
geocode_error     = конкретная ошибка либо "Адрес не найден" / "ФИАС не найден"
```

Техническая геометрия не должна трактоваться как подтверждённая координата.

### Авторизация

`401/403` — фатальная ошибка batch. Оставшиеся строки текущей системы остаются `pending`, чтобы после исправления ключа продолжить работу.

### Rate limit и сеть

После исчерпания retries конкретная строка становится `failed`, а цикл может продолжиться. В последовательном режиме для 429 действует дополнительный cooldown. Сетевые ошибки из известного transient-списка и timeout повторяются.

### Отмена

Отмена:

- abort-ит активные HTTP-запросы;
- прекращает получение новых chunk;
- переводит оставшиеся `pending` в `failed`;
- завершает задание со статусом `failed` и сообщением «Отменено пользователем».

Уже успешно записанные строки остаются `geocoded`.

### Повторный запуск

Повторный запуск слоя:

1. запрещается, если для слоя уже есть активное задание;
2. переводит все `failed` обратно в `pending`;
3. сохраняет уже `geocoded` без изменений;
4. создаёт новое задание;
5. обрабатывает сумму бывших `failed` и оставшихся `pending`.

Для адресного импорта колонка берётся из metadata слоя либо передаётся явно. Текущий retry endpoint ориентирован на адресную колонку; отдельный публичный retry-путь, восстанавливающий ФИАС-режим из `geocodeFiasColumn`, в нём не реализован.

## 11. Переносимый псевдокод

```text
function importExcel(file, selectedColumn, mode):
    rows = parseFirstSheet(file, headerRow=1)
    job = createJob(total=count(nonEmptyRows), status="processing")

    for row in rows:
        createItem(
            sourceValue=row[selectedColumn],
            status="pending",
            geometry=null
        )

    enqueue(runGeocoding(job.id, mode))
    return job.id

function runGeocoding(jobId, mode):
    while ids = nextPendingIds(jobId, limit=200):
        if jobCancelled(jobId):
            abortActiveRequests()
            markRemainingPendingAsFailed("Отменено пользователем")
            finishJob("failed")
            return

        items = loadItems(ids)

        if mode == "address":
            settings = readTransportSettingsNow()
            results = runAddressWorkers(items, settings)
        else:
            results = runFiasSequentially(items)

        transaction:
            for result in results:
                if result.success:
                    validateFiniteCoordinates(result)
                    updateItem(
                        status="geocoded",
                        geometry=[result.lon, result.lat],
                        normalizedAddress=result.formattedAddress,
                        fiasId=result.fiasId,
                        precision=result.precision
                    )
                else:
                    updateItem(status="failed", error=result.error)
            updateJobProgress()

    finishJob("completed")

function geocodeAddressWithRetry(item, settings):
    if trim(item.address) == "":
        return failure("Пустой адрес")

    for attempt from 0 to settings.retries:
        if cancelled(): return failure("Прервано")
        waitForGlobalRateSlot(settings.rps, settings.jitterMs)

        try:
            response = POST suggest/address
                timeout=settings.timeoutMs
                connectionReuse=not settings.pseudoSingle

            if response.status in [401, 403]:
                throw FatalAuthError
            if response.status == 429:
                throw RetryableRateLimitError
            if response.status is not 2xx:
                return failure("HTTP " + response.status)

            first = response.json.suggestions[0]
            if first missing or coords missing or coords not numeric:
                return failure("Адрес не найден")
            return success(normalize(first))

        catch retryableError:
            if attempt == settings.retries:
                return failure(retryableError.message)
            sleep(settings.backoffMs * (attempt + 1) + randomJitter())
```

Псевдокод использует строгий общий rate slot. Текущий Node.js код достигает среднего общего RPS паузами каждого worker, как описано выше.

## 13. Чек-лист внедрения в другой системе

### Безопасность

- [ ] API-ключ хранится только на сервере в secret manager/переменной окружения/зашифрованном хранилище.
- [ ] Браузер никогда не вызывает DaData с ключом напрямую.
- [ ] Ключ и заголовок Authorization исключены из логов и трассировок.
- [ ] Доступ к изменению ключа и транспорта ограничен администраторами.
- [ ] Адреса в диагностике сокращаются или редактируются по принятой политике.

### Контракт

- [ ] Реализован точный URL `suggest/address`, `POST`, JSON и `Token`.
- [ ] Отправляются `query` и `count: 1`.
- [ ] Берётся только первый suggestion.
- [ ] Валидируются наличие и числовой формат `geo_lat`/`geo_lon`.
- [ ] Координаты сохраняются как `[lon, lat]`.
- [ ] Сохраняются нормализованный адрес, ФИАС ID и уровень точности.
- [ ] Пустой результат не считается успешным.

### Batch

- [ ] Есть общий лимит RPS, а concurrency не умножает его.
- [ ] Есть per-request timeout и внешняя отмена.
- [ ] Retry разрешён только для transient network error, timeout и 429.
- [ ] 401/403 останавливают задание.
- [ ] Backoff линейный; jitter настраиваемый.
- [ ] Есть отключаемое keep-alive reuse.
- [ ] Статус каждой строки и прогресс задания долговечны.
- [ ] Повтор обрабатывает только pending/failed.
- [ ] Два задания не обрабатывают один набор строк одновременно.

## 14. Чек-лист приёмочного тестирования

### Одиночный запрос

- [ ] Корректный ключ и точный адрес возвращают HTTP 200 и координаты.
- [ ] Проверены `value`, `fias_id`, `fias_level`, `geo_lat`, `geo_lon`.
- [ ] Пустой `suggestions` обрабатывается без падения.
- [ ] Ответ без координат не создаёт точку.
- [ ] Неверный ключ даёт управляемую ошибку 401/403 и не повторяется.
- [ ] В логах нет ключа.

### Малый XLS/XLSX (10–20 строк)

Включить: точный адрес, неточный адрес, пустую ячейку, несуществующий адрес и дубликат.

- [ ] Используется первый лист и первая строка как заголовок.
- [ ] Пользователь может выбрать адресную или ФИАС-колонку.
- [ ] Слой/набор строк создаётся сразу, геокодирование продолжается в фоне.
- [ ] Пустая строка получает понятную ошибку.
- [ ] Успешные строки имеют `[lon, lat]`, адрес, precision и возможный ФИАС ID.
- [ ] Неуспешные строки имеют `failed`, но не ложную успешную точку.
- [ ] Прогресс достигает terminal-состояния.
- [ ] Отмена прекращает новые запросы.
- [ ] Повторный запуск не трогает уже успешные строки.

### Большой XLS/XLSX

Размер должен быть близок к реальной эксплуатации и включать разные типы адресов.

- [ ] Измерены фактический RPS и число одновременно открытых запросов.
- [ ] Общий RPS не растёт пропорционально concurrency.
- [ ] Проверены последовательный и планируемый параллельный режимы.
- [ ] Сравнены keep-alive и `pseudoSingle` на проблемном сетевом пути.
- [ ] Искусственно проверены timeout, reset и 429.
- [ ] Retries соответствуют 2/4/6 секундам при defaults.
- [ ] После рестарта/сбоя сохранённые статусы позволяют безопасно продолжить.
- [ ] Нет двух активных jobs на один набор строк.
- [ ] Проверены доли success/failed и отсутствие необъяснимых `[0,0]`.
- [ ] Изменение транспорта применяется к следующему batch без рестарта.
