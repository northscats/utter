---
name: Состояние durable-запуска
description: Правила выхода из фонового восстановления и безопасного административного повтора.
---

Фоновый durable-запуск не должен оставлять защищённый модуль в промежуточном состоянии после исключения. Ошибка переводит запуск в отдельное конечное состояние, а повтор выполняет весь restore/reconcile, а не только последнюю сверку.

**Why:** Если исключение остаётся только в журнале, сохранённое `restoring` одновременно закрывает финансовые данные и запрещает оператору восстановиться без перезапуска приложения.

**How to apply:** Сериализовать старт и ручной повтор одним process lock, хранить только безопасный код этапа, держать потребителей остановленными до успешной сверки и запускать их идемпотентно после `ready`. В development согласовывать уже существующую локальную БД без полного App Storage restore; при публикации и ручном retry выполнять restore полностью. Пока production restore идёт, HTTP GET/HEAD должен отвечать лёгкой стартовой заглушкой без БД, чтобы routing probes не занимали worker threads; доступ открывать сразу после reconcile, не дожидаясь safety backup. Если watchdog работает в Gunicorn master, состояние долгого restore нужно передавать ему через атомарный межпроцессный marker с конечным максимальным временем; Python-состояние worker после fork для этого ненадёжно.

Production может быть liveness-ready и при этом не пройти durable restore: эти состояния нужно анализировать раздельно. Долгий построчный restore в одной транзакции может потерять PostgreSQL SSL-соединение уже после успешного запуска HTTP.

**Why:** Восстановление данных и доступность процесса имеют разные критерии успеха; зелёный `/healthz` не доказывает, что финансовая история восстановлена.

**How to apply:** Для restore нужны pre-ping/recycle и повтор с новым соединением после `OperationalError`, а лучше — идемпотентные чанки с промежуточными commit/checkpoint. После ошибки restore защищённые data-dependent маршруты должны явно оставаться в degraded/recovery-состоянии, даже если liveness продолжает отвечать 200.

Корневой durable manifest не должен содержать все защищённые строки одним JSON-массивом. Таблицы нужно хранить в неизменяемых чанках, ограниченных сериализованным размером; особо большая строка получает отдельный чанк, а legacy-конвертация читает исходный manifest потоково и переключает `latest` через CAS только после проверки всех чанков.

**Why:** Manifest около 233 МБ с дублированными снимками лимитов раздувался в Python более чем до 1,2 ГБ и приводил к SIGKILL production worker до первой checkpoint-записи.

**How to apply:** Root хранит counts, ID-index и ссылки с checksum; restore читает по одному чанку и сразу commit-ит особо большие строки. Не подтверждать миграцию формата на малом fixture: сначала прогонять точную копию live manifest с замером peak RSS, сохраняя неизменяемый predecessor для rollback.
