# Оповещение об изменениях лимитов: эксплуатация

## Назначение и границы данных

Модуль работает с вручную загружаемыми полными перечнями ГИС РЭБ.
Разные области охвата должны храниться в разных наборах отчётности.
Дата среза вводится оператором; дата имени файла не используется.
УИН — строка с точкой, а не число и не идентификатор предприятия ОСВ.
Отсутствие объекта в следующей форме означает только отсутствие в выгрузке.

Денежные показатели выражены в **тысячах рублей**. Годовое финансирование,
предельная стоимость и накопительные показатели «на 01.01» — отдельные
показатели, которые нельзя складывать между собой. Пустота, прочерк и ноль
различаются. Повторяющиеся УИН сохраняют все строки мероприятий.

## Ежедневная работа

1. Открыть «Оповещение о лимитах» из списка модулей.
2. Выбрать набор с подходящей областью охвата.
3. Загрузить XLSX, указав фактическую дату среза.
4. Дождаться проверки и открыть предварительное сравнение.
5. Проверить проблемы данных и неоднозначные соответствия строк.
   Решение не должно подменять отсутствие данных нулём или искусственно
   связывать независимые строки.
6. Проверить пару сравниваемых версий, суммы, даты и исходные координаты.
7. Подтвердить версию. Только это действие обновляет актуальный реестр и
   создаёт автоматические уведомления.

Первый принятый срез — база сравнения, а не массовая рассылка о появлении
всех объектов. Повтор принятого файла не создаёт новый срез и рассылку.
Просмотр или экспорт исторического сравнения не публикует версию.
Если другой оператор уже принял новую базу, прежнее сравнение необходимо
пересчитать перед подтверждением.

## Подключение MAX

Без токена интерфейс должен показывать **«MAX не подключён»**.
Записи очереди без реального ответа MAX не считаются успешной отправкой.
В рамках разработки используются тесты с подменой транспорта; наличие
этих тестов не означает проверку реального бота.

Подключение выполняет администратор после отдельного разрешения владельца.
Сохранённый полный комплект настроек означает постоянную работу бота:

1. Подготовить бота, токен и ID согласованной админ-группы.
2. Передать токен только через защищённые настройки;
   не отправлять его в чат, URL, логи или диагностические файлы.
   Служебный секрет webhook создаётся автоматически, хранится зашифрованным
   и не показывается оператору. Ранее сохранённый секрет сохраняется.
3. Проверить доверенную TLS-цепочку до MAX. При необходимости установить
   доверенный сертификат удостоверяющего центра. Не отключать TLS-проверку.
4. Сделать бота администратором согласованной группы.
5. Обновить публикацию и открыть «Настройки» в опубликованном приложении.
   Выбрать основной набор и сохранить настройки. Отдельного включения нет:
   сохранение запускает проверку приёмника, регистрацию webhook и после
   подтверждения — отправку очереди.
   Приложение проверяет совпадение служебного секрета с опубликованным
   приёмником до обращения к MAX: preview с отдельной БД не может
   перенаправить события в несовместимый production.
   При отказе/таймауте регистрации отправки приостанавливаются без потери
   очереди; приложение повторяет подключение с ограниченной задержкой и
   использует тот же секрет после перезапуска.
   В production-настройке LIMITS_MAX_WEBHOOK_URL должен содержать полный
   HTTPS-адрес webhook текущей публикации. Адрес берётся из проверенных
   метаданных публикации и не строится из Host или proxy-заголовков запроса.
   Переменная должна присутствовать именно в окружении запущенной публикации.
   В preview адрес намеренно не наследуется: это исключает отправку секрета
   на подменённый Host или в установку с другой базой.
   Если проверочный GET webhook возвращает 404, опубликована старая версия
   приложения: токен и ID группы ещё не проверяются, пока публикация не обновлена.
   После проверки приёмника приложение запрашивает у MAX администраторов
   указанной группы: так до подписки проверяются токен, ID группы и доступ бота.
   Страница показывает «Работает», «Подключается повторно» либо безопасную
   причину, последнюю попытку, последнее успешное подключение и следующий
   повтор. Токен и служебный секрет в диагностике не выводятся.

Поле «Реестр объектов для подписок бота» выбирает набор срезов ГИС РЭБ,
в котором бот проверяет введённые УИН и к которому относит подписки.
Это не группа MAX и не отдельная загружаемая версия. Если набор один,
оператор выбирает его.
6. На согласованных тестовых адресатах проверить регистрацию, одобрение,
   отказ, несколько подписок, отписку, отзыв доступа и остановку бота.
7. Только после проверки разрешать рабочие рассылки.

Webhook и long polling — альтернативы; не запускать оба источника событий
одновременно. Секрет проверяется по заголовку `X-Max-Bot-Api-Secret`.
HTTP-подтверждение события означает его долговечное принятие системой,
а не выполнение всех связанных отправок.

Администраторы сайта и администраторы MAX-группы — разные полномочия.
Бот не создаёт веб-учётные записи. Решение из MAX разрешено только человеку
из актуального списка администраторов строго настроенной группы.
При невозможности проверить список решение не принимается.

Телефон, введённый вручную, **не подтверждает владение номером**.
Корректные контрольные цифры ИНН **не подтверждают связь человека
с организацией**; это оценивает модератор.

## Очередь и ошибки

Автоматические и ручные уведомления имеют фиксированные содержание,
получателя и связь с версией. Перед фактической отправкой снова проверяются
согласие, доступ, подписка и отсутствие остановки бота.

Успешный ответ API означает **«принято MAX»**, а не «доставлено»
или «прочитано». Сетевой таймаут после передачи запроса может означать,
что MAX принял сообщение, но ответ не дошёл. Такой исход требует
отдельного решения оператора. Повтор может создать дубликат:
exactly-once не гарантируется без соответствующего контракта провайдера.

Не исправлять состояния очереди прямым SQL в рабочей базе. Использовать
доступные администратору повтор или явную отмену с сохранением причины.
Ошибки авторизации устранять в защищённых настройках, не вставляя токен
в диагностику.

## История и восстановление

Доступны десять последних подтверждённых версий, включая актуальную.
История сообщений не хранится отдельно сверх этого окна. При вытеснении
версии удаляются её исходник, снимок, связанные сравнения, отчёты,
сообщения и попытки отправки. Сравнение удаляется, если из окна вышла
любая его сторона.

Незавершённые отправки вытесняемой версии блокируют публикацию следующей
версии. Нужно дождаться их завершения либо явно отменить их. Очередь
нельзя молча удалять ради принятия нового файла.

Администратор может вручную удалить и принятую версию, включая текущую,
после подтверждения удаления исходника и связанной истории.
При удалении текущей версии актуальной становится последняя оставшаяся
принятая версия (по времени принятия); при её отсутствии текущий срез
очищается. Присутствие объектов и реквизиты пересчитываются по оставшемуся
срезу. Переключение не создаёт повторных уведомлений. Обрабатываемые
загрузки и версии с незавершёнными отправками защищены от удаления.

Получатели, текущие подписки, решения о доступе и минимальная идентичность
объектов сохраняются. Подписка на отсутствующий объект не является
архивом старой финансовой формы.

Ошибочные и отклонённые загрузки очищаются отдельно через 72 часа
(`LIMITS_TEMP_TTL_HOURS`, по умолчанию `72`). Очистка проверяется при запуске
и затем каждый час. Она не вытесняет подтверждённые версии.
Удаление локальных исходников выполняется после фиксации решения в БД;
незавершённая очистка повторяется.

Исходники и записи модуля включаются в существующее долговечное
резервирование приложения. Копирование выполняется вне HTTP-ответа.
Локальный файл сам по себе не заменяет внешнюю резервную копию.
Ручное удаление версии в той же транзакции записывает отдельную
сохраняемую отметку (tombstone). Она не удаляется при обычном
вытеснении истории и не создаётся
при обычном вытеснении старейшей версии после принятия 11-го среза.
Отметка отсекает версию, её снимки, сравнения, очередь и исходный файл при
аддитивном восстановлении из ещё старого manifest. После фиксации транзакции
приложение также обновляет маленький внешний sidecar в App Storage; при
недоступности хранилища повтор выполняется перед следующим removal-aware
снимком. Поэтому полный durable backup не выполняется в HTTP-запросе, а
отсутствие sidecar не отменяет уже зафиксированное удаление в БД.
После восстановления сверка окна истории должна завершиться **до**
открытия исторических страниц и возобновления отправок.

Старые общие резервные копии могут содержать удалённые версии.
Удаление из рабочего модуля не обещает немедленного физического удаления
из таких копий. Их хранение и удаление регулируются отдельной политикой
ротации общих резервных копий; нельзя удалять общую копию ОСВ только
потому, что в ней есть старая версия лимитов. При восстановлении всегда
применяется действующее окно истории, независимо от возраста копии.

## Проверки перед вводом

Автоматические проверки выполняются из `osv-dashboard` стандартным
`python -m unittest`; сервисные наборы, которые подменяют конфигурацию
Flask/БД, запускаются отдельными процессами.

Контрольные результаты для согласованных форм:

- форма 1: 2545 строк, 2516 УИН;
- форма 2: 2563 строки, 2535 УИН;
- между формами: 20 новых объектов, один отсутствующий;
- смена программного кода не делает существующий УИН новым объектом;
- исчезновение отдельной строки не делает отсутствующим весь объект;
- суммы сравниваются без потери десятичной точности;
- все три даты отслеживаются отдельно.

Рабочий Gunicorn сохраняет один процесс worker: другие модули приложения
также используют внутрипроцессные фоновые исполнители. Не увеличивать
число worker без отдельной проверки координации фоновых задач.
