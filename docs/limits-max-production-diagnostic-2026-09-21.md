# Диагностика MAX-бота лимитов — 21 сентября 2026

## Итог

Проверена активная публикация `https://gisuzter.replit.app`.

Первопричина находится **до обращения к MAX API**: в production-базе нет
настроек MAX и нет выбранного набора лимитов. Production-база при этом не
пустая: в ней есть пользователи и общие настройки приложения, но отсутствуют
наборы лимитов, записи исходящей очереди и доставки модуля.

Контрольное сообщение не отправлялось. Это ожидаемый безопасный результат:
без production-токена, числового ID группы, выбранного набора и служебного
секрета нельзя обращаться к MAX или создавать сообщение с неопределённым
адресатом. Повторная отправка не выполнялась.

## Проверенные стадии

| Стадия | Результат | Безопасное доказательство |
|---|---|---|
| Активная публикация | Успешно | Публикация активна, текущая сборка успешна, доступ публичный |
| HTTPS и маршрут webhook | Успешно | `GET /limit-notifications/max/webhook` вернул JSON и HTTP 403 без заголовка секрета |
| Версия приёмника | Успешно | Маршрут существует; это не HTTP 404 старой публикации |
| Совпадение служебного секрета | Не проверено | В production нет сохранённого секрета |
| Авторизация токена MAX | Не проверено | В production нет сохранённого токена |
| Числовой ID и доступ к группе | Не проверено | В production нет сохранённого ID группы |
| Видимость администраторов | Не проверено | Проверка MAX не запускалась без токена и ID группы |
| Регистрация подписки webhook | Не выполнена | Нет полного production-комплекта настроек |
| Контрольная отправка | Не выполнена | До транспортного вызова MAX дело не дошло |
| Исходящая очередь | Пуста | Нет сообщений бота и доставок; зависших или неизвестных исходов нет |

Ответ HTTP 403 без секрета является правильным поведением границы webhook и
не раскрывает секрет. Токен и служебный секрет не читались и не выводились.

## Категория отказа

Категория: **production-конфигурация и данные модуля**, а не TLS, токен MAX,
ID чата, права бота, подписка MAX или обработка очереди.

Конкретный блокирующий факт: production не содержит полного комплекта
`токен + ID админ-группы + набор данных + служебный секрет`. Поэтому
reconciler не может выполнить preflight приёмника и не обращается к MAX.

## Требуемое действие оператора

1. В опубликованном приложении создать или восстановить нужный набор лимитов.
2. Открыть настройки модуля именно в публикации, а не в preview.
3. Сохранить токен согласованного бота, числовой ID админ-группы и выбрать
   production-набор лимитов. Служебный секрет приложение создаст само.
4. Убедиться, что production-переменная `LIMITS_MAX_WEBHOOK_URL` содержит
   канонический адрес:
   `https://gisuzter.replit.app/limit-notifications/max/webhook`.
5. Дождаться статуса «Работает». Только после успешных проверок приёмника,
   списка администраторов и регистрации подписки выполнить **одну**
   явно помеченную тестовую отправку в согласованную группу.
6. Если отправка получит неопределённый сетевой исход, не повторять её
   автоматически; сначала проверить группу и журнал.

Изменение кода по результату проверки не требуется: опубликованный маршрут
правильно закрыт секретом, а очередь не выдаёт отсутствие конфигурации за
успешную отправку.
