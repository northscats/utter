# Инструкция для Replit Agent: приём и обработка вложений через IMAP

Ниже находится готовое техническое задание. Его можно целиком передать Replit Agent
в другом приложении.

---

## Готовый запрос агенту

Нужно добавить в существующее приложение Replit интеграцию с почтовым ящиком по
IMAP, аналогичную модулю «Анализ ФХД РСО».

Важно: не нужно разворачивать собственный почтовый сервер. Приложение должно быть
IMAP-клиентом и подключаться к уже существующему почтовому ящику по защищённому
соединению IMAPS/TLS.

Перед изменениями:

1. Изучи стек, структуру приложения, механизм авторизации, текущую БД, способ
   хранения файлов и существующие фоновые процессы.
2. Не заменяй используемую БД, систему авторизации или файловое хранилище.
3. Используй стандартный для проекта способ миграции схемы.
4. Для секретов используй Replit Secrets. Не проси вставлять пароль в чат, код,
   Git или обычный конфигурационный файл.

### Требуемое поведение

Добавь административный раздел «Почтовый сервер IMAP» со следующими полями:

- хост IMAP, например `imap.yandex.ru`;
- порт, по умолчанию `993`;
- логин почтового ящика;
- пароль приложения;
- папка, по умолчанию `INBOX`;
- интервал опроса в минутах, по умолчанию `30`, минимум `5`;
- флаг включения автоматической синхронизации.

Добавь действия:

- «Проверить подключение» — подключиться по TLS, выполнить вход, открыть папку в
  режиме `readonly` и показать понятный результат;
- «Синхронизировать сейчас» — выполнить один цикл обработки;
- «Сохранить настройки»;
- просмотр времени и результата последней синхронизации.

Доступ к настройкам, проверке соединения, ручной синхронизации и правилам должен
быть только у администратора. Для изменяющих запросов должна действовать CSRF-защита.

### Хранение секретов

Предпочтительный вариант:

- `IMAP_PASSWORD` хранить как Replit Secret;
- настройки без секрета хранить в БД или переменных окружения;
- интерфейс должен показывать только признак «пароль задан», но не расшифрованный
  пароль.

Если пароль обязательно должен редактироваться через административный интерфейс:

- хранить его в БД только в зашифрованном виде;
- ключ `ENCRYPTION_KEY` хранить только в Replit Secrets;
- использовать аутентифицированное шифрование, например Fernet;
- пустое поле пароля при повторном сохранении означает «оставить прежний пароль»;
- никогда не возвращать пароль API-клиенту и не подставлять расшифрованное значение
  в HTML;
- не логировать пароль, строку подключения и полное содержимое писем.

### Правила маршрутизации писем

Создай таблицу правил маршрутизации. Каждое правило содержит:

- идентификатор целевого объекта приложения, например предприятия или проекта;
- маску отправителя;
- маску темы;
- приоритет;
- признак активности;
- необязательный комментарий.

Сопоставление выполняй без учёта регистра через glob-маски:

- отправитель: `*@example.ru`;
- точный адрес: `reports@example.ru`;
- тема: `ОСВ *`;

Для `From` проверяй и полный декодированный заголовок, и извлечённый email-адрес.
Если заданы обе маски, должны совпасть обе. Первым применяется активное правило с
наименьшим приоритетом. Если правило не найдено, письмо не помечать обработанным:
после добавления правила его можно будет обработать повторно.

### Получение писем

Для каждого цикла:

1. Создать TLS-контекст через системное хранилище доверенных сертификатов.
2. Подключиться через IMAP SSL с тайм-аутом 15–20 секунд.
3. Авторизоваться и открыть настроенную папку.
4. Получить непрочитанные сообщения.
5. Декодировать MIME-заголовки `From`, `Subject` и имена вложений.
6. Найти подходящее правило маршрутизации.
7. Извлечь только разрешённые типы вложений.
8. Передать каждый файл в существующий обработчик загрузки приложения, не
   дублируя бизнес-логику парсинга.
9. После успешной или окончательно отклонённой обработки сохранить результат.
10. Закрыть IMAP-соединение и удалить временные файлы в блоке `finally`.

Не полагайся только на флаг `UNSEEN`: пользователь может вручную вернуть письму
статус «непрочитано». Для идемпотентности создай журнал обработанных сообщений с
уникальным ограничением по:

- идентификатору почтового аккаунта;
- `UIDVALIDITY`;
- IMAP UID сообщения.

Дополнительно сохрани `Message-ID`, дату, отправителя, тему, статус, количество
вложений и краткую ошибку. Перед обработкой проверяй журнал. Запись об успехе и
созданные бизнес-данные фиксируй согласованно, чтобы перезапуск не создавал
дубликаты.

### Вложения и безопасность

Список расширений сделай конфигурируемым. Для сценария анализа ФХД по умолчанию
разреши:

- `.xls`;
- `.xlsx`;
- `.zip`.

Обязательно:

- ограничить максимальный размер письма, одного вложения и суммарный размер;
- нормализовать имя через `basename`, генерировать безопасное внутреннее имя и не
  доверять MIME-имени;
- не позволять вложению задавать абсолютный путь или `../`;
- проверять фактический формат, а не только расширение;
- для ZIP проверять Zip Slip, число файлов, вложенные архивы и коэффициент
  распаковки;
- извлекать только разрешённые файлы;
- использовать отдельный временный каталог на письмо;
- удалять временный каталог независимо от результата;
- не выполнять макросы и содержимое вложений;
- не помечать письмо успешно обработанным, если сохранение файла или бизнес-операция
  завершилась ошибкой.

Используй постоянное файловое хранилище, уже принятое в приложении. Не рассчитывай
на локальную файловую систему Replit как на долговременное хранилище, если проект
уже использует App Storage или другое постоянное хранилище.

### Фоновый процесс

Не запускай бесконтрольно отдельный IMAP-поток в каждом web worker.

Выбери вариант, соответствующий архитектуре приложения:

1. отдельный workflow/worker для IMAP — предпочтительно для нескольких web worker;
2. планировщик с блокировкой-лидером в PostgreSQL;
3. один web worker и один защищённый от повторного запуска daemon-thread — допустимо
   только для небольшого приложения, если это ограничение явно зафиксировано.

Фоновый цикл должен:

- запускаться идемпотентно;
- использовать application context, если он требуется фреймворком;
- ждать настроенный интервал через прерываемое ожидание;
- продолжать работу после сетевой ошибки;
- корректно завершаться по SIGTERM;
- не выполнять параллельно два цикла синхронизации одного ящика;
- иметь тайм-ауты на сеть и обработку файлов.

Не запускай процесс отдельной shell-командой вручную. Настрой или обнови штатный
Replit Workflow. Сервис должен слушать `PORT`, если это web-процесс.

### Обработка ошибок и наблюдаемость

Разделяй как минимум:

- неверную аутентификацию;
- недоступность сети или DNS;
- ошибочный порт;
- отсутствие папки;
- ошибку декодирования письма;
- запрещённый или слишком большой файл;
- ошибку бизнес-обработчика;
- временную ошибку БД или файлового хранилища.

Храни и показывай администратору:

- время начала и завершения последней синхронизации;
- количество проверенных писем;
- количество совпавших правил;
- количество обработанных и пропущенных вложений;
- количество обновлённых целевых объектов;
- краткие ошибки без секретов и лишних персональных данных.

### Тесты

Не подключай тесты к реальному почтовому ящику. Замокай IMAP-клиент и проверь:

1. успешное TLS-подключение и открытие папки;
2. ошибку аутентификации и сетевой тайм-аут;
3. корректное декодирование русской MIME-темы и имени вложения;
4. маршрутизацию по адресу и теме без учёта регистра;
5. письмо без правила остаётся доступным для повторной обработки;
6. разрешённые вложения передаются бизнес-обработчику;
7. запрещённые и слишком большие вложения отклоняются;
8. защита ZIP от обхода пути и архивной бомбы;
9. повторный UID не создаёт дубликаты;
10. ошибка обработчика не записывается как успешная;
11. пустой пароль при редактировании не стирает сохранённый секрет;
12. неадминистратор получает отказ на настройках и ручной синхронизации;
13. два одновременных запуска не обрабатывают один ящик параллельно.

После реализации:

- запусти миграции только штатным способом проекта;
- перезапусти соответствующий workflow;
- проверь логи запуска;
- выполни один end-to-end проход через интерфейс с тестовым ящиком или локальным
  IMAP mock-сервером;
- сообщи перечень изменённых файлов, необходимых секретов и порядок настройки;
- не показывай значения секретов.

### Критерии готовности

- Администратор может настроить IMAP и проверить соединение.
- Ручная синхронизация показывает понятный результат.
- Автоматическая синхронизация переживает временные сетевые ошибки.
- Письма маршрутизируются по управляемым правилам.
- Вложения проходят через существующий бизнес-обработчик.
- Повторный запуск не создаёт дубликаты.
- Секреты не находятся в коде, Git, HTML, API-ответах или логах.
- В многопроцессной конфигурации работает только один планировщик IMAP.
- Все тесты проходят, workflow запускается без ошибок.

## Справочные особенности реализации «Анализ ФХД РСО»

В исходном модуле используются:

- IMAPS на порту `993`;
- папка `INBOX`;
- интервал опроса `30` минут с минимумом `5` минут;
- поиск непрочитанных писем;
- glob-маски отправителя и темы через `fnmatch`;
- обработка `.xls`, `.xlsx` и `.zip`;
- маршрутизация письма к предприятию;
- ручные действия «Проверить подключение» и «Синхронизировать сейчас»;
- источник загрузки `auto_imap`;
- один Gunicorn worker с потоками, чтобы не запускать несколько IMAP-циклов.

При переносе следует сохранить пользовательский сценарий, но добавить журнал UID
и не показывать расшифрованный пароль в форме — это делает новую реализацию
устойчивее и безопаснее исходной.
