## Обязательные блокеры MAX

Старые права связаны с recipient/dataset/UIN, новая модель — user/UIN,
а выбор источника — immutable version. Автоматически переносить
`approved`, подписки, отказы и согласия нельзя. Числовое преобразование
MAX ID само по себе не доказывает эквивалентность прав. При **любых строках**
в старых MAX таблицах preflight останавливается даже при наличии новых:
необходимо отдельное согласование и проверяемый перенос/архивный режим.
Не очищайте таблицы ради обхода проверки! Флага обхода нет.
Этот пакет **не решает legacy-to-new permissions**.

`max_dataset_scope.migrate_selected_version()` при отсутствии
`max_limits_version_id` читает `max_limits_dataset_id`, выбирает текущую
accepted-версию либо записывает пустое значение через `select_version()`.
Последний также отменяет недоставленные outbox других версий (при пустом
выборе — все). Поэтому SQL ничего из этого не повторяет, не сбрасывает
существующий выбор (включая явно пустой), не исправляет права и не отменяет
outbox. При отсутствии нового ключа и наличии старого непустого выбора
или непустой outbox — блокер до отдельного решения. Отсутствие ключа
на чистой установке допускается; последующее поведение startup не является
частью этой миграции.

`max_bot_config.py` хранит credentials и enabled/generation в
`osv-dashboard/private/max-bot.json`, использует lock-файл и права 0700/0600.
Это **не таблица и не SQL-backfill**. Сохранить закрытый persistent volume
и его права, не печатать содержимое/токен и не переносить секреты в SQL.
SQL не меняет enabled и не запускает, не отправляет и не ставит сообщения.

## Почему успешного COMMIT недостаточно для запуска

Текущий startup имеет самостоятельные побочные эффекты:

* **`limits_schema.migrate_limits_schema()` удаляет все десять перечисленных
  выше старых MAX таблиц, даже пустые, и settings с префиксами `limits_max_`
  и `limits_bot_`.** SQL этого не делает. Следовательно, даже успешно
  мигрированный baseline с пустыми legacy таблицами нельзя запускать с
  нынешним startup при требовании сохранять ВСЕ исторические объекты.
  Нужен отдельный релиз с недеструктивным startup. Здесь также выполняется
  `limit_row_snapshots.object_id DROP NOT NULL`; это не новое изменение
  периода: оно уже было в startup до cutoff. Если внешний baseline его
  пропустил, это отдельный долг схемы. `progress_json` startup добавляет
  с SQL DEFAULT `'{}'`, что отличается от чистого ORM; наш SQL не переписывает
  существующий default и не заполняет старые строки.
* `migrate_max_limits_schema()` удаляет `telegram_limits_{outbox,cursors,subscriptions}`
  и настройки `telegram_limits_offset`, `telegram_limits_username`.
  Их наличие блокируется SQL (даже пустые таблицы): требуется отдельно
  исправленный безопасный startup, не удаление исторических объектов.
* `seed_monthly_indices()` добавляет отсутствующие месяцы из
  `analog_monthly_indices.INITIAL_INDICES`. В SQL нет бизнес-значений.
  Их происхождение/согласование и автоматический seed требуют отдельного решения.
* `_purge_retired_module_grants()` удаляет из `user_module_access` права
  `module_key='investment_reconciliation'`. SQL сохраняет их без изменений;
  это ещё одна причина не запускать текущий startup при требовании сохранить
  все данные/права.
* `_reconcile_limits_after_restore()` вызывает rename legacy dataset,
  миграцию выбранной версии, `cleanup_purged_files()`,
  `cleanup_temporary_versions()` и `reconcile_history_window()`.
  Восстановление durable backup, ротация истории и физические удаления —
  **не часть этого SQL**. Не запускать приложение для проверки миграции.
* Запуск worker при включённом MAX может обработать сохранённые очереди.
  Приложение, workers, импорт/restore/cleanup и webhook должны оставаться
  остановлены/изолированы до отдельной приёмки. Этот SQL не меняет их настройки.

## Частичные установки и испытания

Полностью отсутствующие новые таблицы создаются; совместимые существующие
проверяются по типам, размерам, nullable/default, PK/UNIQUE и индексам.
Допускается восстановление пропущенных индексов/constraints и nullable колонок;
NOT NULL колонка без достоверного backfill — только в пустой таблице.
Отсутствующий идентификатор, неожиданная колонка/default/constraint/UNIQUE,
невалидный индекс, нештатная sequence, RLS или relation другого вида —
явная ошибка, без исправления/удаления данных. Дополнительные неуникальные
индексы не удаляются. При ошибке проверки uniqueness при создании constraint
вся транзакция откатывается. Это не универсальный инструмент schema repair.

Матрица обязательных sandbox-тестов PostgreSQL:

* baseline cutoff + dry-run: schema/data/маркер неизменны;
* apply на пустом MAX, затем повторный apply и dry-run: одинаковая схема,
  отсутствуют seed/сообщения/cleanup intents;
* частичная схема: пропущенный индекс, nullable колонка, пустая новая таблица;
* несовместимые тип/nullable/default/UNIQUE/index, занятое имя sequence,
  отсутствующий prerequisite: ненулевой exit code, без изменений public;
* NOT NULL колонка отсутствует в непустой таблице: отказ без backfill;
* каждая legacy MAX таблица с данными, Telegram объект/settings,
  старый выбор без нового ключа: отказ и полное сохранение;
* существующие новая выбранная версия, права, outbox, индексы месяцев:
  не изменяются ни при apply, ни при повторе;
* удержанная блокировка другим соединением: timeout и полный rollback.

Ни один тест не должен подключаться к production или запускать приложение.

### Фактически выполненные локальные проверки

На изолированном PostgreSQL **16.10**, отдельный Unix socket, без TCP и без
запуска приложения, построена схема из SQLAlchemy metadata коммита b6c27fb.
Успешно проверены:

* dry-run с побайтовым сравнением нормализованного `pg_dump` до/после;
* apply, повторный apply и повторный dry-run;
* точное сравнение семи новых таблиц с PostgreSQL DDL текущего ORM:
  все колонки/defaults, PK/UNIQUE и индексы;
* восстановление nullable колонки/индекса, обязательной колонки пустой таблицы
  и пропущенного UNIQUE constraint;
* откаты при несовместимом типе/default/nullable/индексе, дополнительном UNIQUE,
  отсутствующем prerequisite, NOT NULL колонке непустой таблицы;
* сохранение всей БД при ошибке создания UNIQUE на дубликатах;
* блокеры legacy recipient, Telegram-таблицы, старого выбора без нового,
  непустой outbox без нового выбора;
* неизменность существующих нового выбора, approved UIN, outbox и месячного
  индекса (синтетические данные только sandbox);
* совместимость startup-default `progress_json='{}'`, timeout при удержанной
  другой сессией блокировке.

Это не проверка внешней production БД. Для её конкретной схемы остаются
обязательны испытания на восстановленной копии, сверка всего исторического
содержимого и отдельно согласованный план MAX/startup. Каждый отдельный
вариант старых таблиц/нестандартных sequences/внешних зависимостей в локальной
матрице не воспроизводился.
