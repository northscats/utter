# MAX: диагностика внешнего Docker-сервера

Проверять нужно контейнер на вашем сервере, а не preview Replit.
Диагностический экран не запускает бота и не отправляет сообщения.
Сам запуск бота может обработать накопленную очередь.

## Что означает «подключён, затем ошибка»

В polling запись `polling connected` означает успешные проверки токена,
группы, прав и первый ответ `/updates`. Она появляется **до** обработки
полученных команд, сохранения курсора и отправки ответов. Поэтому повтор
`connected → failed` не доказывает ошибку токена: возможны ошибка обработчика,
несовместимая схема БД, отказ исходящей отправки, ошибка следующего запроса.

После обновления откройте «Лимиты → Бот MAX», блок диагностики.
Передайте разработчику только стадию, код причины, HTTP-статус и время.
Не передавайте конфигурацию целиком, токены, ключи, тела сообщений,
дампы запросов или строки подключения к БД.

## Обновление образа

1. В интерфейсе остановите бота и согласуйте окно обновления.
2. Сделайте резервную копию БД, файлов и закрытой конфигурации.
3. Если используется `image: osv-dashboard-web:latest`, изменение файлов
   рядом с Compose **не изменяет образ**. В каталоге обновлённого
   `osv-dashboard`, где находятся Dockerfile и requirements.txt, выполните:

   ```sh
   docker build -t osv-dashboard-web:max-diagnostics .
   ```

4. Укажите `image: osv-dashboard-web:max-diagnostics` в вашем Compose.
   Если сборка выполняется на другой машине, доставьте этот образ через
   закрытый registry либо `docker save`/`docker load`.
5. Сначала завершите перенос `/app/private`, описанный ниже. Затем:

   ```sh
   docker compose up -d --no-deps --force-recreate web
   docker compose logs --tail=150 web | grep -iE 'MAX|startup|DB ready'
   ```

Не используйте `docker compose down -v`: это удаляет тома с данными.
Обновление не требует запускать бота: сначала осмотрите диагностику.
Текущий процесс приложения должен работать в одном Gunicorn worker.

## Сохранение настроек перед пересозданием

Настройки MAX находятся в `/app/private`. Если том для него отсутствует,
они живут только в контейнере. **Нельзя сначала подключить пустой том:**
он скроет существующие файлы.

После остановки бота, но до удаления или пересоздания контейнера:

```sh
umask 077
mkdir -p ./max_bot_private
docker compose cp web:/app/private/. ./max_bot_private/
```

Если копирование не удалось — остановитесь. Не создавайте пустую
конфигурацию взамен и не выводите содержимое файлов в терминал.
Проверьте наличие копии локально без показа секретов.
Эта папка должна находиться вне публичной раздачи и вне контекста сборки.
Не добавляйте её в Git или пересылаемые архивы.

Подключите скопированную папку в `web.volumes`:

```yaml
- ./max_bot_private:/app/private
```

Выставьте владельца под пользователя **вашего образа** (штатный образ:
UID/GID 10001), права каталога 0700 и файла `max-bot.json` 0600.
Не переключайте одновременно `user: root` на другого пользователя без
проверки прав остальных томов. Работа под root не исправляет сетевые ошибки.

## Режимы подключения

Для локального теста polling:

```yaml
MAX_LIMITS_WEBHOOK_URL: ""
MAX_LIMITS_REQUIRE_WEBHOOK: "0"
```

Проверьте отсутствие другого активного экземпляра с тем же ботом.
Существующая подписка webhook у MAX не удаляется от очистки переменной:
изменять её должен уполномоченный администратор после согласования.

Для внешнего сайта в корне домена:

```yaml
SCRIPT_NAME: ""
MAX_LIMITS_WEBHOOK_URL: "https://YOUR-DOMAIN/limit-notifications/max/webhook"
MAX_LIMITS_REQUIRE_WEBHOOK: "1"
```

Если сайт размещён под `/osv`, задайте `SCRIPT_NAME: "/osv"` и добавьте
`/osv` в путь URL. Запись `${SCRIPT_NAME:-/osv}` подставляет `/osv`
даже при пустой переменной — учитывайте это в своём Compose.
Наличие непустого webhook URL выбирает webhook, даже если REQUIRE равен 0.

Reverse proxy должен пропускать POST без redirect/login/Basic Auth/WAF
challenge и сохранять `X-Max-Bot-Api-Secret`. Требуются публичный DNS и
действующий HTTPS с полной цепочкой. Открытие URL в браузере (GET) не
проверяет доставку событий. Регистрация подписки не доказывает получение
подписанного события; это отдельная стадия.

## Чего не делать при ошибке

- Не отключать TLS-проверку. Убедиться, что в образе есть
  `/app/certs/russian-trusted-root-ca.pem`.
- Не удалять курсор, очередь, заявки или события, чтобы «пропустить ошибку».
- Не повторять массовую отправку для диагностики.
- Не менять ключ шифрования без плана переноса зашифрованных данных.
- Раскрытые пароли и ключи заменить согласованно, без включения их в логи.

Без диагностики **с внешнего сервера** конкретная причина его отказа
не установлена. Локальные тесты с подменённым API подтверждают обработку
ошибок, но не доступность MAX из вашей сети.
